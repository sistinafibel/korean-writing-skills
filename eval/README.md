# 스킬 평가

이 폴더에는 이 저장소의 스킬을 사용하면 한국어 출력이 얼마나 달라지는지 확인하는 테스트가 있습니다. 같은 모델에 같은 입력을 보내고 시스템 프롬프트에 넣는 지침만 바꿔서 출력을 생성한 뒤, 규칙 검사와 블라인드 판정, 나란히 보는 비교표로 비교합니다.

## 실행

Node.js 20 이상과 로그인된 Claude Code CLI(`claude`)가 필요하고, 다른 패키지는 설치하지 않습니다. 저장소 루트에서 아래 명령을 실행하면 격리 확인, 생성, 규칙 검사, 판정, 토큰 측정, 보고서 작성이 차례로 진행됩니다.

```sh
node eval/run.mjs
```

결과는 `eval/results/<오늘 날짜>/` 에 저장됩니다. 이미 끝난 생성과 판정은 건너뛰므로, 중간에 멈췄다면 같은 명령을 다시 실행해서 이어서 진행할 수 있습니다. 스킬 문서를 수정한 뒤에 다시 실행하면 그 스킬이 들어간 조건만 다시 생성하고 다시 판정합니다.

| 옵션 | 기본값 | 설명 |
| --- | --- | --- |
| `--run <이름>` | 오늘 날짜 | 결과 폴더의 이름입니다. 모델을 바꿔서 실행할 때에는 다른 이름을 지정합니다. |
| `--model <모델>` | `claude-sonnet-5-5` | 출력을 생성하는 모델입니다. |
| `--judge-model <모델>` | `claude-opus-5-5` | 블라인드 판정에 사용하는 모델입니다. |
| `--runs <횟수>` | 3 | 조건마다 케이스마다 생성하는 횟수입니다. |
| `--concurrency <수>` | 4 | 동시에 실행하는 호출의 수입니다. |
| `--cases <목록>` | 전체 | 쉼표로 구분한 케이스 식별자입니다. |
| `--comparisons <목록>` | 전체 | 쉼표로 구분한 비교 식별자입니다. 지정한 비교에 들어가는 조건만 생성하고 판정합니다. |
| `--update-readme` | 꺼짐 | 루트 README 의 벤치마크 절을 이 실행의 결과로 다시 작성합니다. |
| `--skip-isolation` | 꺼짐 | 격리 확인 단계를 건너뜁니다. |

단계를 하나씩 실행할 수도 있습니다. 모델을 호출하지 않는 `check-rules.mjs` 와 `report.mjs` 는 검사 기준이나 보고서 형식을 수정한 뒤에 다시 실행해도 비용이 들지 않습니다.

```sh
node eval/verify-isolation.mjs   # 다른 지침이 섞이지 않는지 확인
node eval/generate.mjs           # 출력 생성
node eval/check-rules.mjs        # 규칙 검사
node eval/judge.mjs              # 블라인드 판정
node eval/measure-tokens.mjs     # 시스템 프롬프트의 토큰 수 측정
node eval/report.mjs             # 비교표와 요약 작성
```

## 비교하는 조건

조건은 `conditions.json` 에 정의되어 있습니다. 조건마다 지침 문서의 프런트매터를 제거하고 본문만 `<skill name="...">` 으로 감싸서 시스템 프롬프트에 넣습니다.

| 조건 | 시스템 프롬프트에 넣는 지침 | 적용하는 케이스 |
| --- | --- | --- |
| `baseline` | 없음 | 전체 |
| `fluent-korean` | [snflkd/fluent-korean](https://github.com/snflkd/fluent-korean) 의 출력 스타일 문서 | 전체 |
| `ours` | 이 저장소의 `natural-korean` 과 `git-writing-korean` | 전체 |
| `im-not-ai` | [epoko77-ai/im-not-ai](https://github.com/epoko77-ai/im-not-ai) 의 `quick-rules.md` | 글을 고쳐 쓰는 갈래 |
| `ours-before-optimization` | 커밋 `bfbcb53` 의 두 스킬 (git-writing-korean 의 분량을 줄이기 전) | 커밋 케이스와 PR 케이스 |
| `ours-two-examples` | natural-korean 의 예시를 조항당 2개로 줄인 실험용 사본과 `git-writing-korean` | 전체 |

- fluent-korean 과 im-not-ai 의 문서는 이 저장소에 복사하지 않습니다. 실행할 때 `conditions.json` 에 고정해 둔 커밋의 주소에서 내려받아 `eval/.cache/` 에만 저장하고, 이 폴더는 git 에서 제외되어 있습니다. 두 저장소의 라이선스는 모두 MIT 입니다.
- im-not-ai 는 이미 작성된 글을 여러 단계로 윤문하는 도구이고 스크립트로 검증하는 단계를 포함합니다. 이 테스트에서는 한 번의 호출에 사용하는 규칙집만 시스템 프롬프트에 넣었으므로, 그 도구를 원래 방식대로 사용한 결과와 다를 수 있습니다. 그래서 글을 고쳐 쓰는 갈래에만 적용하고 별도의 비교로 판정합니다.
- 실험용 사본(`experiments/natural-korean-two-examples.md`)은 `experiments/make-two-examples.mjs` 가 natural-korean 원본에서 예시 5개를 지워서 만듭니다. 원본은 수정하지 않습니다.

비교는 네 가지입니다. `main` 은 `baseline`, `fluent-korean`, `ours` 를 모든 케이스에서 비교하고, `rewrite-tools` 는 고쳐 쓰는 갈래에서 `im-not-ai` 를 더해서 비교합니다. `git-optimization` 은 커밋 케이스와 PR 케이스에서 분량을 줄이기 전과 후의 스킬을 비교하고, `two-examples` 는 예시를 줄인 사본과 원본을 모든 케이스에서 비교합니다.

## 조건을 격리하는 방법

이 PC 의 Claude Code 에 설정된 CLAUDE.md, rules, 출력 스타일, 플러그인이 출력에 영향을 주면 조건 사이의 비교가 성립하지 않습니다. 그래서 모든 호출을 아래 옵션으로 실행합니다(`lib/claude.mjs`).

```sh
claude -p --safe-mode --system-prompt-file <조건의 지침 파일> --tools "" --strict-mcp-config \
  --disable-slash-commands --setting-sources "" --no-session-persistence --effort medium \
  --model <모델> --output-format json
```

- `--safe-mode` 는 CLAUDE.md, 스킬, 플러그인, 훅, 출력 스타일을 비활성화하고, `--setting-sources ""` 는 사용자 설정과 프로젝트 설정을 읽지 않게 합니다.
- 도구와 MCP 서버를 전달하지 않고, 저장소 밖의 빈 폴더를 작업 폴더로 사용합니다.
- 이 스크립트를 Claude Code 세션 안에서 실행하더라도 부모 세션의 환경 변수가 전달되지 않도록, 인증에 필요한 변수를 제외한 `CLAUDE*` 환경 변수를 제거합니다.
- 인증은 CLI 에 저장된 로그인 정보를 그대로 사용하고, 키나 토큰을 이 저장소의 파일에 기록하지 않습니다.

`verify-isolation.mjs` 는 로컬 프록시로 실제 API 요청의 본문을 확인합니다. 2026-11-24 에 확인한 결과는 다음과 같고, 실행할 때마다 `results/<실행>/isolation-check.json` 에 기록됩니다.

- 지침이 없는 조건의 system 에는 CLI 가 항상 추가하는 식별 문장 한 줄(`You are a Claude agent, built on Anthropic's Claude Agent SDK.`)만 있었습니다.
- 지침이 있는 조건의 system 에는 그 식별 문장과 넣어 준 지침만 있었습니다.
- 사용자 메시지에는 CLI 가 추가하는 계정 이메일 안내와 실행 환경 정보(작업 폴더, 운영체제, 날짜)가 함께 들어갔습니다. 이 두 가지는 문장 작성에 관한 지침이 아니고 모든 조건에 똑같이 들어갑니다.
- CLAUDE.md, rules, 출력 스타일, 스킬 목록, 응답 언어 설정은 요청에 없었고, 전달된 도구도 없었습니다.

## 케이스

케이스는 `cases/` 에 있는 Markdown 파일입니다. 프런트매터에 갈래와 검사 종류를 적고, 본문 전체를 사용자 메시지로 보냅니다.

| 갈래 | 케이스 | 내용 |
| --- | --- | --- |
| 설명 답변 | `01-explain-build-error` | CI 에서만 실패하는 빌드의 원인 설명 |
| 설명 답변 | `02-explain-locking` | 낙관적 잠금과 비관적 잠금 가운데 선택 |
| 작업 결과 보고 | `03-report-work` | 느린 회원 목록 화면을 수정한 작업의 결과 보고 |
| 화면 문구 | `04-ui-payment-error` | 카드사 점검 시간에 결제가 거절되었을 때의 오류 팝업 |
| 화면 문구 | `05-ui-auto-category` | 가계부 앱의 자동 분류 기능 안내문 |
| AI 문체 고쳐 쓰기 | `06-rewrite-tech-retro` | 캐시 도입 회고 단락 |
| AI 문체 고쳐 쓰기 | `07-rewrite-running-essay` | 아침 달리기 경험담 |
| 끊어 쓴 문장 합치기 | `08-merge-short-sentences` | 택배 예약 도움말 |
| 커밋 메시지 | `09-commit-fix-coupon-timezone` | 시간대 버그 수정 |
| 커밋 메시지 | `10-commit-feature-order-export` | CSV 내보내기 기능 추가 |
| PR 제목과 본문 | `11-pr-feature-reminder-hours` | 마이그레이션과 환경 변수가 포함된 기능 추가 |
| PR 제목과 본문 | `12-pr-fix-cart-quantity` | 배포할 때 참고할 내용이 없는 버그 수정 |

- 입력에 사용한 diff 와 상황 설명은 모두 이 테스트를 위해 지어낸 내용입니다.
- 고쳐 쓰기 케이스의 원문에는 '단순히 ~가 아니라', '~하는 순간', 불필요한 '우리', 평가만 담은 수식어, 과도한 쉼표를 일부러 넣었습니다.
- 작업 기록과 PR 상황 설명은 개발자가 메모하듯이 작성했습니다. 명사로 끝나는 항목과 화살표, "눌러 봤는데" 같은 구어 표현이 들어 있어서, 모델이 그 표현을 그대로 옮기는지도 확인할 수 있습니다.
- 결과를 확인한 뒤에 케이스를 수정했다면 수정한 이유를 이 문서의 "케이스 수정 기록" 절에 남깁니다.

## 규칙 검사

`lib/rules.mjs` 가 출력마다 아래 항목을 셉니다. 코드 블록과 인라인 코드 안의 글자는 세지 않습니다.

| 대상 | 항목 |
| --- | --- |
| 모든 케이스 | 가운뎃점, 엠대시, 엔대시, 화살표, 이모지의 수 |
| 모든 케이스 | '단순히 ~가 아니라', 'A를 넘어 B', '~하는 순간', 주어 '우리', 평가만 담은 수식어, '정리하면' 같은 반복 정리 표지의 수 |
| 모든 케이스 | 문장당 쉼표 수, 쉼표가 3개 이상인 문장의 비율, 명사형이나 연결어미로 끝난 문장의 비율 |
| 커밋 케이스 | 타입이 목록에 있는지, 제목이 명사형으로 끝나는지, 제목 설명이 55자 이하인지, 제목에 조사를 사용했는지, 괄호 나열이 없는지, 메시지만 출력했는지, 본문이 해라체인지, 사용하지 않는 어휘의 수 |
| PR 케이스 | 제목 검사 전체, 절 이름과 순서, 배포 참고 사항 절의 유무, 확인하지 못한 항목의 `[ ]` 표시, 합니다체, 세션 링크와 서명, 사용하지 않는 어휘의 수 |

"규칙 위반 수"는 출현 수의 합에 통과하지 못한 형식 검사의 수를 더한 값이고, 문장 통계는 포함하지 않습니다.

이 검사에는 다음과 같은 한계가 있습니다.

- 정규식으로 세기 때문에 문맥을 판단하지 못합니다. 팀을 가리키는 정당한 '우리'나 근거를 함께 작성한 '효율적인'도 한 건으로 셉니다.
- 평가만 담은 수식어는 natural-korean 조항에 있는 7개와 같은 종류의 6개(획기적, 탁월한, 뛰어난, 완벽한, 근본적, 본질적)만 셉니다.
- 제목의 조사 사용 여부는 낱말의 마지막 글자로 추정합니다.
- 커밋 타입, 제목 끝맺음, 절 이름은 이 저장소의 스킬만 정하고 있는 기준입니다. 이 기준을 받지 않은 조건이 통과하지 못하는 것은 당연하므로, 이 항목들은 스킬을 넣었을 때 기준이 실제로 지켜지는지를 확인하는 용도로 봐야 합니다.

## 블라인드 판정

판정 기준과 판정 모델에게 보내는 지시는 [rubric.md](rubric.md) 에 있습니다. 판정 모델은 조건 이름을 알 수 없고 두 스킬의 조항도 받지 않으며, 명확성, 자연스러움, 정보량, 지시 준수를 1~5점으로 평가하고 순위를 정합니다. 같은 묶음을 순서를 뒤집어서 두 번 판정하고, 보고서에 자리별 순위 평균과 두 판정의 1위 일치율을 함께 표시합니다.

## 결과 폴더의 파일

| 파일 | 내용 |
| --- | --- |
| `side-by-side.md` | 케이스마다 조건별 출력을 나란히 놓은 비교표입니다. 사람이 직접 읽고 판단하는 자료입니다. |
| `summary.md` | 조건별 핵심 수치, 갈래별 수치와 케이스별 수치, 실험 결과, 실행 정보입니다. |
| `notes.md` | 결과를 읽고 사람이 작성한 해석입니다. 스크립트가 덮어쓰지 않습니다. |
| `rule-checks.md`, `rule-checks.json` | 규칙 검사의 항목별 표와 출력별 원본 값입니다. |
| `judgments.json` | 묶음마다 기호와 조건의 대응, 점수, 순위, 판정 이유입니다. |
| `tokens.json` | 조건별, 스킬 부분별 입력 토큰 수입니다. |
| `outputs/<케이스>/<조건>.<번호>.md` | 생성된 출력의 원본입니다. |
| `generation.json`, `meta.json`, `isolation-check.json` | 호출별 사용량, 실행 정보, 격리 확인 결과입니다. |
