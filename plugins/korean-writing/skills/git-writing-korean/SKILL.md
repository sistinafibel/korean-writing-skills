# 커밋 메시지와 PR 문서 작성 기준

제목만 읽어도 무엇이 변경되었는지 알 수 있고, 본문을 읽으면 변경한 이유와 확인한 내용까지 알 수 있게 작성합니다. 저장소의 commitlint가 허용하는 타입과 PR 템플릿의 절이 이 문서보다 우선하고, 나머지는 저장소에서 이전에 사용하던 문체와 다르더라도 이 문서를 따릅니다.

## 제목

커밋 제목과 PR 제목은 같은 규칙으로 작성합니다. PR에 커밋이 여러 개 있으면 그 커밋들을 합친 결과 하나를 제목으로 작성합니다.

```
<타입>: <무엇을 어떻게 변경하는지>
```

| 타입 | 사용하는 경우 |
|------|---------------|
| `feature` | 기능 추가 |
| `fix` | 잘못된 동작 수정 (긴급한 운영 수정 포함) |
| `refactor` | 동작을 유지한 구조 변경 |
| `perf` | 동작을 유지한 속도 향상이나 자원 사용량 감소 |
| `docs` | 문서만 변경 |
| `test` | 테스트만 추가하거나 수정 |
| `chore` | 의존성, 설정, 빌드 도구 변경 |
| `ci` | CI 워크플로 변경 |
| `deploy` | 배포 설정이나 배포 스크립트 변경 |

`feat`, `bugfix`, `hotfix`, `update`는 사용하지 않습니다. commitlint가 위 타입을 허용하지 않는 저장소에서는 허용되는 타입 가운데 의미가 가장 가까운 타입을 선택합니다.

설명은 50자 안팎의 **명사형** 으로 끝내고, 끝맺는 형태는 아래 순서로 정합니다.

1. 동작을 나타내는 한자어 명사가 있으면 그 명사로 끝냅니다: 추가, 삭제, 제거, 수정, 변경, 반환, 차단, 제한, 표시, 비활성화. "추가함"처럼 "-함"을 덧붙이지 않습니다.
2. 고유어 동사는 "-ㅁ/-음"으로 끝냅니다: 숨김, 늘림, 줄임, 옮김.
3. 변경한 뒤의 상태를 설명하는 구절은 "함"으로 끝냅니다: `재시도하는 동안에는 결제 버튼을 누를 수 없게 함`

- 끝맺음만 명사형으로 줄이고 그 앞의 조사는 생략하지 않습니다.
- "-한다", "-했다", "-합니다", "-기", "-으로"로 끝내지 않고, "숨김 처리"처럼 의미가 없는 명사를 덧붙이지 않습니다.
- 괄호 안에 여러 항목을 나열하지 않습니다. 버전 번호 같은 짧은 참조 하나만 제목 끝에 괄호로 표시할 수 있습니다.
- 커밋 하나에는 변경 한 가지만 포함하고, 서로 다른 변경을 "그리고"로 연결해야 한다면 커밋을 나눕니다.
- 범위를 표시해야 한다면 `<타입>(<범위>): ...` 형식으로 작성합니다.

| 나쁜 예 | 좋은 예 |
|---------|---------|
| `주문 내보내기·포장 목록 메뉴 추가` | `feature: 주문 내보내기 메뉴와 포장 목록 메뉴를 추가` |
| `feat: 회원 가입에 휴대폰 인증 단계를 추가한다` | `feature: 회원 가입에 휴대폰 인증 단계를 추가` |
| `feature: 주문 목록 페이지 크기 상한 맞추기` | `feature: 주문 목록의 페이지 크기를 최대 100건으로 제한` |
| `fix: 품절 상품 구매 버튼 숨김 처리함` | `fix: 품절된 상품의 구매 버튼을 숨김` |
| `fix: 쿠폰 발급 로직 개선 (정책 분리, 일시 실패 503)` | `fix: 쿠폰 발급이 일시적으로 실패하면 503을 반환` (정책 분리는 별도의 커밋) |

## 커밋 본문

제목만으로 변경한 이유를 알 수 없을 때 작성합니다. 완성된 문장과 해라체("-했다")로, 변경한 이유를 먼저 쓰고 변경한 방법을 그다음에 씁니다. 한 줄은 72자 안팎에서 줄을 바꾸고, 관련 이슈는 마지막 줄에 `Refs: #12` 또는 `Closes: #12`로 표시합니다.

```
fix: 예외 로그의 경로에 포함된 URL 쿼리 값을 마스킹

스테이징 환경에서 쿼리에 식별용 값을 넣어 요청해 보니 예외 필터가 기록하는
path에 그 값이 그대로 남아 있었다. 예외 필터도 접근 로그와 같은
함수(redactQuery)로 쿼리 값을 마스킹하도록 수정했다.
```

## PR 본문

**합니다체** 로 작성하고 해요체는 사용하지 않습니다. 절 이름과 순서는 아래와 같이 고정하며, 다른 이름(요약, 왜, 변경 내용, 검증, 테스트 계획)은 사용하지 않습니다.

```markdown
## 작업 배경

<이 변경이 필요해진 상황(누가 어떤 문제를 겪었는지, 무엇을 측정했는지)을 2~4문장으로 작성하고, 관련 이슈나 이전 PR을 링크합니다. 버그 수정이면 증상과 원인을 모두 작성합니다.>

## 변경 사항

- **<변경된 동작을 요약한 15자 안팎의 구절>**: <머지하면 동작이 어떻게 달라지는지 한두 문장>

## 배포 참고 사항

- <마이그레이션, 환경 변수, 배포 순서, 기존 데이터의 변화>

## 확인 사항

- [x] <직접 실행한 명령과 그 결과(테스트 개수 포함), 추가한 테스트가 검증하는 내용>
- [ ] <확인하지 못한 항목과 그 이유, 또는 배포한 뒤에 확인할 항목>
```

- 작업 배경, 변경 사항, 확인 사항은 반드시 작성하고, 변경 규모가 작으면 각 절을 한 줄로 작성할 수 있습니다.
- 입력이나 작업 기록에 있는 사실은 절 구성에 맞추느라 누락하지 않고 가장 가까운 절에 작성합니다. 반대로 거기에 없는 사실이나 확인하지 않은 효과는 추가하지 않습니다.
- 변경 사항에는 변경한 파일이 아니라 달라지는 동작을 작성합니다. 동작과 관련이 적은 변경은 마지막에 "그 밖에" 항목으로 모읍니다.
- 배포 참고 사항은 해당하는 내용이 없으면 "없음"이라고 쓰지 않고 절 전체를 생략합니다. 변경이 없다는 사실을 직접 확인했다면 확인 사항에 작성합니다: `- [x] DB 스키마, 환경 변수, 배포 순서의 변경 없음`
- 확인 사항에는 직접 실행한 것만 `[x]`로 표시하고, 확인하지 못한 항목은 생략하지 않고 `[ ]`로 표시합니다.
- 에이전트 세션 링크, "Generated with" 같은 서명, 이모지, "이 PR은 ~을 합니다" 같은 도입 문장은 작성하지 않습니다.
- 리뷰 지적 번호(D4, P2)만 표시하지 않고 무엇이 변경되었는지를 문장으로 작성합니다.

```markdown
## 작업 배경

배송지를 입력하지 않은 주문은 결제 화면에 안내 문구만 표시되고 배송지 입력 화면으로
이동할 방법이 없어서, 지난주에 같은 내용의 문의가 12건 접수되었습니다.

## 변경 사항

- **배송지 입력 화면으로 이동**: 결제 화면의 안내 문구 아래에 "배송지 입력하기" 버튼을
  추가했습니다. 버튼을 누르면 해당 주문의 배송지 입력 시트가 열립니다.

## 확인 사항

- [x] `pnpm test` 214개 통과 (버튼을 누르면 배송지 입력 시트가 열리는지 검증하는 E2E 1개 추가)
- [x] DB 스키마, 환경 변수, 배포 순서의 변경 없음
- [ ] 실제 PG 결제: 로컬 환경에서는 테스트 결제만 확인했습니다
```

## 어휘와 기호

개발 문서에서 통용되는 어휘를 사용합니다. 대상과 동작을 정확하게 가리키는 한자어 동사(추가, 삭제, 제거, 수정, 변경, 반환, 차단, 비활성화, 연동, 기록)를 우선 사용하고, 비유적인 표현이나 특정 작성자만 사용하는 표현은 사용하지 않습니다. 아래 표에 없는 표현도 같은 기준으로 판단합니다.

| 사용하지 않는 표현 | 대신 사용하는 표현 |
|--------------------|--------------------|
| 메뉴를 더한다, 기능을 얹는다 | 메뉴를 추가한다, 기능을 추가한다 |
| 단계를 뺀다, 화면을 걷는다 | 단계를 제거한다, 화면을 삭제한다 |
| 넘어가는 길이 끊긴 곳 | 다음 화면으로 이동할 수 없는 화면 |
| 503을 돌려준다 | 503을 반환한다 |
| 버튼을 막는다 | 버튼을 비활성화한다 |
| 눌러 봤습니다, 돌려 봤습니다 | 직접 실행해서 확인했습니다 |
| 로그에 찍힌다, 서버가 죽는다 | 로그에 기록된다, 서버가 종료된다 |
| 코드를 다듬는다, 손본다, 정리한다 | 실제로 변경한 내용(이름을 변경한다, 중복 코드를 제거한다) |

영문, 숫자, 코드 표기 뒤에 오는 조사는 붙여 씁니다: `PR을`, `503을`, `version이`.

아래 기호는 단어 사이의 관계를 함축하므로 제목과 본문에 사용하지 않습니다. 코드 블록, 인용한 원문, 파일 이름처럼 원문 그대로 표기해야 하는 부분에는 사용할 수 있습니다.

| 기호 | 나쁜 예 | 좋은 예 |
|------|---------|---------|
| 가운뎃점 `·` | `주문서·영수증 화면 추가` | `주문서 화면과 영수증 화면을 추가` |
| 엠대시 `—`, 엔대시 `–` | `결제 실패 — 재시도 버튼 추가` | `결제에 실패하면 재시도 버튼을 표시` |
| 화살표 `→` | `CI 제한 시간 20분 → 35분` | `CI 제한 시간을 20분에서 35분으로 늘림` |

## natural-korean 검사

커밋 메시지와 PR 문서에도 같은 스킬셋의 **natural-korean** 스킬의 조항을 적용합니다. 제목은 표제이므로 완성된 문장으로 끝내는 조항만 적용하지 않습니다.

초안을 작성한 뒤 커밋하거나 PR을 올리기 전에, 그리고 이미 올라간 문구를 점검할 때 다음과 같이 검사합니다. natural-korean 스킬을 불러와서 조항과 예시를 읽고(이 대화에서 이미 불러왔다면 다시 불러오지 않습니다), 초안의 문장을 하나씩 그 조항과 이 문서의 기준에 비추어 확인한 뒤, 어긋난 문장을 고쳐 쓰고 나서 올립니다. 커밋과 PR에서는 아래 항목을 자주 놓칩니다.

- 조사를 생략했거나 '~의'로 명사만 이어 붙인 구절
- 원인과 결과를 연결어미로 잇지 않고 짧은 문장 여러 개로 나눈 부분
- "개선", "최적화", "안정화"처럼 평가만 담은 표현(측정한 값이나 확인한 사실로 바꿉니다)
- "단순한 수정이 아니라", "~하는 순간", 실제 주체가 아닌 "우리"
- 작업 배경에 쓴 내용을 변경 사항에서 반복한 부분과 본문 끝에 덧붙인 요약 문단
