# 커밋 메시지와 PR 문서 작성 기준

이 문서는 모든 저장소에서 커밋 메시지와 PR 제목, PR 본문을 같은 구조와 같은 말투로 쓰기 위한 기준입니다. 목표는 처음 보는 사람이 제목만 읽고도 무엇이 바뀌었는지 알고, 본문을 읽고 나면 왜 바뀌었는지와 무엇을 확인했는지까지 납득하는 것입니다.

문장을 쓰는 방법(성분을 생략하지 않기, 조사와 어미를 살리기, 비유 대신 일반 어휘 쓰기, 평가만 담은 수식어와 상투적인 문형 피하기)은 같은 스킬셋의 **natural-korean** 스킬을 그대로 따릅니다. natural-korean 은 커밋 메시지에 "프로젝트의 관례"를 따르라고 하는데, 이 문서가 바로 그 관례입니다.

## 1. 우선순위

1. 저장소의 `commitlint.config.*` 가 허용하는 타입이 가장 우선합니다. 훅이 거절하는 타입은 쓰지 않습니다.
2. 저장소에 `.github/pull_request_template.md` 가 있으면 그 절을 채웁니다. 템플릿에 없는 절(예: 배포 참고 사항)이 필요하면 템플릿 절 뒤에 덧붙입니다.
3. 그 밖의 모든 것은 이 문서를 따릅니다. 저장소마다 예전에 쓰던 말투가 다르더라도 새로 쓰는 문구는 이 문서에 맞춥니다.

## 2. 커밋 제목

### 형식

```
<타입>: <무엇을 어떻게 바꾸는지>
```

- 범위가 꼭 필요하면 `<타입>(<범위>): ...` 로 씁니다. 예: `chore(release): v1.4.0 (빌드 10208)`
- 설명은 **해라체 평서형 "-한다"** 로 끝냅니다. 명사형(`추가`, `뺌`), "-기", "-으로" 같은 끝맺음은 쓰지 않습니다.
- 길이는 50자 안팎으로 유지합니다. 넘치면 내용을 본문으로 옮깁니다.
- 괄호로 여러 항목을 나열하지 않습니다. 명세 버전이나 버전 번호처럼 짧은 참조 하나만 끝에 괄호로 붙일 수 있습니다.
- 한 커밋에는 한 가지 변경만 담습니다. 제목에서 서로 다른 일을 "그리고"로 이어야 한다면 커밋을 나눕니다.

### 타입

| 타입 | 쓰는 경우 |
|------|-----------|
| `feature` | 사용자나 호출자가 새로 할 수 있는 일이 생길 때 |
| `fix` | 잘못된 동작을 바로잡을 때 (급한 운영 수정도 `fix` 로 씁니다) |
| `refactor` | 동작은 그대로 두고 구조만 바꿀 때 |
| `perf` | 동작은 그대로 두고 속도나 자원 사용을 줄일 때 |
| `docs` | 문서만 바꿀 때 |
| `test` | 테스트만 더하거나 고칠 때 |
| `chore` | 의존성, 설정, 빌드 도구처럼 제품 동작과 무관한 정리를 할 때 |
| `ci` | CI 워크플로를 바꿀 때 |
| `deploy` | 배포 설정이나 배포 스크립트를 바꿀 때 |

- `feat`, `bugfix`, `hotfix`, `update` 는 쓰지 않습니다. 새 기능은 `feature` 로, 버그 수정은 급한 정도와 상관없이 `fix` 로 씁니다.
- 저장소의 commitlint 가 위 표의 타입을 거절하면 그 저장소가 허용하는 가장 가까운 타입을 고릅니다.

commitlint 를 쓰는 저장소라면 `type-enum` 을 위 표와 같게 맞춰 둡니다.

```js
'type-enum': [
  2,
  'always',
  ['feature', 'fix', 'refactor', 'perf', 'docs', 'test', 'chore', 'ci', 'deploy'],
],
```

### 좋은 예와 나쁜 예

| 나쁜 예 | 문제 | 좋은 예 |
|---------|------|---------|
| `주문 내보내기·포장 목록 메뉴 추가` | 타입이 없고, 가운뎃점을 쓰고, 명사형으로 끝남 | `feature: 주문 내보내기와 포장 목록 메뉴를 더한다` |
| `feat: 회원 가입에서 CAPTCHA(보안 확인)를 뺌` | 표에 없는 타입, 명사형 끝맺음 | `feature: 회원 가입에서 CAPTCHA 보안 확인을 뺀다` |
| `feature: 주문 목록을 페이지 크기 상한에 맞추기` | "-기" 끝맺음 | `feature: 주문 목록을 페이지 크기 상한에 맞춘다` |
| `fix: 결제 2~4단계 리뷰 지적 반영 (중복 결제 차단, 재시도 간격 분리, 웹훅 검증 보강)` | 괄호 나열, 세 가지 변경을 한 커밋에 담음 | `fix: 같은 주문의 중복 결제를 막는다` 와 나머지를 각각의 커밋으로 |
| `fix: 쿠폰 발급 리뷰 지적 반영 — 정책을 서비스로 · 일시 실패 503 · 동시성 테스트` | 엠대시와 가운뎃점 나열, "리뷰 지적 반영"은 무엇이 바뀌었는지 말하지 않음 | `fix: 쿠폰 발급이 일시적으로 실패하면 503 을 돌려준다` |

## 3. 커밋 본문

본문은 제목만으로 이유가 드러나지 않을 때 씁니다. 제목과 같은 해라체로 씁니다.

```
fix: 예외 로그의 경로에 남던 URL 쿼리 값을 가린다

스테이징에서 쿼리에 표식 값을 넣어 확인했더니 예외 필터가 남기는 path 에
값이 그대로 남아 있었다. 접근 로그와 같은 함수(redactQuery)를 거치게 했다.
```

- 첫 문단에는 왜 바꾸는지를, 다음 문단에는 무엇을 어떻게 바꿨는지를 씁니다.
- 한 줄은 72자 안팎에서 줄을 바꿉니다.
- 관련 이슈는 마지막 줄에 `Refs: #12` 또는 `Closes: #12` 로 씁니다.

## 4. PR 제목

PR 제목은 커밋 제목과 같은 규칙으로 씁니다. 스쿼시 머지를 하면 PR 제목이 그대로 커밋 제목이 되기 때문입니다. PR 에 커밋이 여러 개 있으면 그 커밋들이 함께 이루는 결과 하나를 제목으로 씁니다.

## 5. PR 본문

PR 본문은 **합니다체** 로 씁니다. 커밋은 개발자가 기록으로 읽고 PR 은 리뷰어와 배포하는 사람이 읽기 때문에 말투를 나눕니다. 해요체("추가했어요")는 쓰지 않습니다.

### 절 구성과 순서

절 이름과 순서는 아래로 고정합니다. 절 이름은 읽는 사람에게 묻거나 지시하는 말("왜", "무엇이 바뀌나")이 아니라, 그 절에 담긴 내용을 가리키는 명사로 씁니다. 다른 이름(요약, 왜, 무엇을, 변경 내용, 검증, 확인, 테스트 계획, 배포 주의)은 쓰지 않습니다.

```markdown
## 작업 배경

<이 변경이 필요해진 상황과 이유. 2~4문장.>

## 변경 사항

- **<바뀐 동작 한 가지>**: <어떻게 바뀌는지 한두 문장>
- ...

## 배포 참고 사항

- <마이그레이션, 환경 변수, 배포 순서, 데이터에 생기는 변화>

## 확인 사항

- [x] <실제로 돌려 보고 통과한 것>
- [ ] <확인하지 못한 것과 그 이유, 또는 배포 뒤에 확인할 것>
```

- **작업 배경**: 반드시 씁니다. 무엇을 바꿨는지가 아니라 바꾸게 된 상황(누가 무엇을 겪었는지, 무엇을 측정했는지)을 씁니다. 관련 이슈나 이전 PR 은 여기에서 링크합니다.
- **변경 사항**: 반드시 씁니다. 파일 목록이 아니라 **동작의 변화** 를 씁니다. 항목마다 굵은 글씨로 바뀐 동작을 먼저 적고, 콜론 뒤에 설명을 이어 씁니다. 사소한 정리는 마지막에 "그 밖에" 아래로 모읍니다.
- **배포 참고 사항**: 마이그레이션, 환경 변수, 배포 순서, 기존 데이터의 변화가 있을 때만 씁니다. 없으면 절을 통째로 빼고, "없음" 이라고 적지 않습니다.
- **확인 사항**: 반드시 씁니다. 실제로 실행한 명령과 결과(테스트 개수 포함)만 `[x]` 로 적습니다. 확인하지 못한 것은 숨기지 않고 `[ ]` 로 적고 이유를 붙입니다.
- 변경이 작아도 절 구성은 같습니다. 그 대신 각 절을 한 줄로 써도 됩니다.

저장소에 PR 템플릿을 둔다면 위 절 구성을 그대로 `.github/pull_request_template.md` 에 넣고, 절마다 쓰는 방법을 HTML 주석으로 달아 둡니다.

### 쓰지 않는 것

- 에이전트 세션 링크, "Generated with" 같은 서명
- 이모지
- 아래 "쓰지 않는 기호" 의 기호
- "이 PR 은 ~을 합니다" 같은 군더더기 첫 문장. 바로 내용으로 들어갑니다
- 근거 없는 평가("크게 개선했습니다", "안정성을 높였습니다"). 대신 측정한 값이나 확인한 사실을 씁니다
- 리뷰 지적 번호(D4, P2)만 적은 항목. 무엇이 바뀌었는지를 문장으로 씁니다

### 쓰지 않는 기호

아래 기호는 낱말 사이의 관계(그리고, 또는, 그래서, 에서 ~로)를 말하지 않고 함축합니다. 읽는 사람이 관계를 짐작해야 하므로 커밋 제목, 커밋 본문, PR 제목, PR 본문 어디에도 쓰지 않습니다. 코드 블록, 인용한 원문, 파일 이름처럼 글자 그대로 옮겨야 하는 부분은 예외입니다.

| 기호 | 이름 | 대신 쓰는 말 |
|------|------|--------------|
| `·` | 가운뎃점 | "와/과", "그리고", "또는", 쉼표 |
| `—` | 엠대시 | 콜론, 마침표로 문장을 나누기, "그래서", "즉" |
| `–` | 엔대시 | 범위는 "~" 또는 "부터 ~까지", 그 밖에는 엠대시와 같음 |
| `→` | 화살표 | "에서 ~로", "~하면 ~한다", "다음에" |

| 나쁜 예 | 좋은 예 |
|---------|---------|
| `주문서·영수증 화면을 더한다` | `주문서와 영수증 화면을 더한다` |
| `CI 제한 시간 20분 → 35분` | `CI 제한 시간을 20분에서 35분으로 늘린다` |
| `바로 구매 — 장바구니 임시 저장을 걷는다` | `바로 구매하면 장바구니를 거치지 않고, 임시 저장 기능을 없앤다` |
| `typecheck · lint · format:check 통과` | `typecheck, lint, format:check 통과` |

## 6. 좋은 PR 본문의 예

```markdown
## 작업 배경

#29 를 올린 뒤 실제 서버(임시 Postgres 에 마이그레이션과 시드)에 화면을 붙여
시나리오 14개를 눌러 봤습니다. 금액 계산과 권한은 모두 맞았지만 화면에서 화면으로
넘어가는 길이 끊긴 곳이 있어서 고칩니다.

## 변경 사항

- **배송지가 비어 결제가 막힌 주문에서 바로 배송지를 채우러 갈 수 있습니다**: 글자뿐이던
  안내를 경고 칸과 "배송지 채우러 가기" 버튼으로 바꾸고, 그 주문의 배송지 시트를 연 채로
  보냅니다.
- **영수증을 발행한 주문은 취소 버튼을 먼저 막습니다**: 전에는 취소 사유를 다 적고 누른
  뒤에야 서버가 거절했다는 것을 토스트로 알 수 있었습니다.
- 그 밖에: CI 제한 시간을 20분에서 35분으로 늘립니다. E2E 가 333개로 늘어서 #29 의
  실행이 320번째에서 끊겼습니다.

## 확인 사항

- [x] 실제 서버 흐름 14개 통과
- [x] `pnpm typecheck`, `lint`, `format:check` 통과, vitest 1,643개 통과
- [ ] 실제 PG 결제 흐름: 로컬에서는 테스트 결제만 확인했습니다
```

## 7. 쓰기 전에 점검할 것

- [ ] 타입이 저장소의 commitlint 에서 허용되고, 위 표의 뜻과 맞는가
- [ ] 제목이 "-한다" 로 끝나고, 괄호 나열이 없는가
- [ ] PR 본문이 합니다체이고, 절 이름과 순서가 기준과 같은가
- [ ] "변경 사항" 이 파일 목록이 아니라 동작의 변화를 말하는가
- [ ] 확인하지 못한 것을 `[ ]` 로 적었는가
- [ ] 세션 링크, 이모지, 가운뎃점(·), 엠대시(—), 엔대시(–), 화살표(→)가 없는가
- [ ] natural-korean 기준으로 문장 성분이나 조사가 빠진 곳, 상투적인 문형이 없는가
