# 커밋 메시지와 PR 문서 작성 기준

이 문서는 모든 저장소에서 커밋 메시지와 PR 제목, PR 본문을 같은 구조와 같은 문체로 작성하기 위한 기준입니다. 처음 보는 사람이 제목만 읽고도 무엇이 변경되었는지 알 수 있고, 본문을 읽으면 변경한 이유와 확인한 내용까지 이해할 수 있게 작성하는 것이 목표입니다.

## 1. 우선순위

1. 저장소의 `commitlint.config.*` 가 허용하는 타입이 가장 우선합니다. commitlint 가 허용하지 않는 타입은 사용하지 않습니다.
2. 저장소에 `.github/pull_request_template.md` 가 있으면 그 템플릿의 절을 채웁니다. 템플릿에 없는 절(예: 배포 참고 사항)이 필요하면 템플릿의 마지막 절 뒤에 추가합니다.
3. 나머지는 모두 이 문서를 따릅니다. 저장소에서 이전에 사용하던 문체가 이 문서와 다르더라도 새로 작성하는 문구는 이 문서에 맞춥니다.

## 2. natural-korean 검사

커밋 메시지와 PR 문서도 사람이 읽는 한국어 글이므로, 같은 스킬셋에 포함된 **natural-korean** 스킬의 조항을 적용합니다. natural-korean 의 동작 범위 2번 조항은 커밋 메시지가 프로젝트의 관례를 따라야 한다고 정하는데, 이 문서가 그 관례에 해당하고, 이 문서는 커밋과 PR 문구에도 natural-korean 조항을 적용하도록 정합니다.

초안을 작성한 뒤 커밋하거나 PR 을 올리기 전에 아래 순서로 검사합니다. 이미 올라간 커밋이나 PR 의 문구를 점검할 때에도 같은 순서를 따릅니다.

1. natural-korean 스킬을 불러와서 조항과 예시를 다시 읽습니다. 기억하고 있는 내용만으로 검사하지 않습니다.
2. 초안의 문장을 하나씩 아래 표에 비추어 확인합니다.
3. 조항에 어긋난 문장을 고쳐 쓰고, 고친 문장을 같은 표로 다시 확인합니다.
4. 어긋난 문장이 남아 있지 않을 때 커밋하거나 PR 을 올립니다.

| natural-korean 조항 | 커밋과 PR 에서 확인할 내용 |
|---------------------|----------------------------|
| 문장 단위 1 (문장 성분) | 무엇이 어디에서 어떻게 변경되는지가 문장에 모두 드러나는가. '~의'로 명사만 이어 붙인 구절이 없는가 |
| 문장 단위 2 (완성된 문장) | 커밋 본문과 PR 본문의 문장이 서술어와 종결어미로 끝나는가. 커밋 제목과 PR 제목은 표제이므로 이 조항 대신 "커밋 제목" 절의 명사형 끝맺음을 따릅니다 |
| 문장 단위 3 (끊어 쓴 문장) | 원인과 결과, 조건과 동작을 짧은 문장 여러 개로 나누지 않고 연결어미로 이어서 썼는가 |
| 문장 단위 4 (쉼표) | 한 문장에 쉼표가 세 개 이상 들어가지 않았는가 |
| 구 단위 1 (조사와 어미) | 제목에서도 조사를 생략하지 않았는가 |
| 구 단위 2, 3 (어휘) | 아래 "어휘" 절의 기준에 맞는가 |
| 구 단위 4 (엠대시) | 아래 "사용하지 않는 기호" 절의 기준에 맞는가 |
| 구 단위 5 (평가만 담은 수식어) | "개선", "최적화", "안정화", "효율적"처럼 평가만 담은 표현을 측정한 값이나 확인한 사실로 바꾸었는가 |
| 상투적인 문형 1~3 | "단순한 수정이 아니라", "~하는 순간", 실제 주체가 아닌 "우리"를 사용하지 않았는가 |
| 글 전체 구성 1 (반복 정리) | 작업 배경에 쓴 내용을 변경 사항에서 반복하지 않았는가. 본문 끝에 요약 문단을 추가하지 않았는가 |

### 어휘

커밋과 PR 에는 개발 문서에서 일반적으로 통용되는 어휘를 사용합니다. 대상과 동작을 정확하게 가리키는 한자어 동사(추가, 삭제, 제거, 수정, 변경, 반환, 차단, 방지, 비활성화, 연동, 기록)를 우선 사용하고, 그 한자어에 조사와 어미를 붙여서 문장으로 완성합니다. 비유적인 표현이나 특정 작성자만 사용하는 표현은 읽는 사람이 의미를 추측해야 하므로 사용하지 않습니다.

| 사용하지 않는 표현 | 대신 사용하는 표현 |
|--------------------|--------------------|
| 메뉴를 더한다, 기능을 얹는다 | 메뉴를 추가한다, 기능을 추가한다 |
| 단계를 뺀다, 화면을 걷는다, 걷어낸다 | 단계를 제거한다, 화면을 삭제한다 |
| 넘어가는 길이 끊긴 곳, 길을 잇는다 | 다음 화면으로 이동할 수 없는 화면, 이동 버튼을 추가한다 |
| 503 을 돌려준다 | 503 을 반환한다 |
| 버튼을 먼저 막는다 | 버튼을 비활성화한다 |
| 화면을 서버에 붙인다 | 화면을 서버와 연동한다 |
| 눌러 봤습니다, 돌려 봤습니다 | 직접 실행해서 확인했습니다, 실행했습니다 |
| 글자뿐이던 안내 | 텍스트로만 표시하던 안내 |
| 로그에 찍힌다 | 로그에 기록된다 |
| 서버가 죽는다, 테스트가 터진다 | 서버가 종료된다, 테스트가 실패한다 |
| 코드를 다듬는다, 손본다, 정리한다 | 실제로 변경한 내용(이름을 변경한다, 중복 코드를 제거한다, 함수를 분리한다) |

위 표의 표현은 기본형으로 표기했으며, 제목에 사용할 때에는 "커밋 제목" 절의 기준대로 명사형으로 끝냅니다. 위 표에 없는 표현도 같은 기준으로 판단합니다. 개발 문서나 공식 문서에서 흔히 사용하는 표현인지 확인하고, 그렇지 않다면 통용되는 표현으로 바꿉니다.

## 3. 커밋 제목

### 형식

```
<타입>: <무엇을 어떻게 변경하는지>
```

- 범위를 표시해야 한다면 `<타입>(<범위>): ...` 형식으로 작성합니다. 예: `chore(release): v1.4.0 (빌드 10208)`
- 설명은 **명사형** 으로 끝냅니다. 커밋 제목은 문장이 아니라 변경 내용을 요약한 표제이고, 한국어 커밋 기록에서 가장 널리 사용하는 형태이기 때문입니다. 끝맺는 형태는 아래 순서로 정합니다.
  1. 동작을 나타내는 한자어 명사가 있으면 그 명사로 끝냅니다: 추가, 삭제, 제거, 수정, 변경, 반환, 차단, 제한, 분리, 적용, 표시, 비활성화. "추가함", "삭제함"처럼 "-함"을 덧붙이지 않습니다.
  2. 고유어 동사는 "-ㅁ/-음"으로 끝냅니다: 숨김, 늘림, 줄임, 옮김, 없앰.
  3. "~하게", "~하도록", "~하지 않게"처럼 변경한 뒤의 상태를 설명하는 구절은 "함"으로 끝냅니다: `재시도하는 동안에는 결제 버튼을 누를 수 없게 함`
- "-한다", "-했다", "-합니다", "-기", "-으로"로 끝내지 않습니다. "숨김 처리", "추가 작업"처럼 의미가 없는 명사를 끝에 덧붙이지도 않습니다.
- 끝맺음만 명사형으로 줄이고 그 앞의 조사는 생략하지 않습니다. `주문 목록 페이지 크기 제한` 대신 `주문 목록의 페이지 크기를 최대 100건으로 제한` 으로 작성합니다.
- 길이는 50자 안팎으로 유지하고, 50자에 담지 못한 내용은 본문에 작성합니다.
- 괄호 안에 여러 항목을 나열하지 않습니다. 명세 버전이나 버전 번호 같은 짧은 참조 하나만 제목 끝에 괄호로 표시할 수 있습니다.
- 커밋 하나에는 변경 한 가지만 포함합니다. 제목에서 서로 다른 변경을 "그리고"로 연결해야 한다면 커밋을 나눕니다.

### 타입

| 타입 | 사용하는 경우 |
|------|---------------|
| `feature` | 사용자나 호출자가 사용할 수 있는 기능을 추가할 때 |
| `fix` | 잘못된 동작을 수정할 때 (긴급한 운영 수정에도 `fix` 를 사용합니다) |
| `refactor` | 동작은 유지하고 구조만 변경할 때 |
| `perf` | 동작은 유지하고 속도를 높이거나 자원 사용량을 줄일 때 |
| `docs` | 문서만 변경할 때 |
| `test` | 테스트만 추가하거나 수정할 때 |
| `chore` | 의존성, 설정, 빌드 도구처럼 제품 동작과 관련이 없는 부분을 변경할 때 |
| `ci` | CI 워크플로를 변경할 때 |
| `deploy` | 배포 설정이나 배포 스크립트를 변경할 때 |

- `feat`, `bugfix`, `hotfix`, `update` 는 사용하지 않습니다. 기능 추가에는 `feature` 를 사용하고, 버그 수정에는 긴급한 정도와 관계없이 `fix` 를 사용합니다.
- 저장소의 commitlint 가 위 표의 타입을 허용하지 않으면 그 저장소가 허용하는 타입 가운데 의미가 가장 가까운 타입을 선택합니다.

commitlint 를 사용하는 저장소에서는 `type-enum` 을 위 표와 동일하게 설정합니다.

```js
'type-enum': [
  2,
  'always',
  ['feature', 'fix', 'refactor', 'perf', 'docs', 'test', 'chore', 'ci', 'deploy'],
],
```

### 좋은 예와 나쁜 예

| 나쁜 예 | 문제 | 좋은 예 |
|---------|------|---------|
| `주문 내보내기·포장 목록 메뉴 추가` | 타입이 없고, 가운뎃점을 사용함 | `feature: 주문 내보내기 메뉴와 포장 목록 메뉴를 추가` |
| `feat: 회원 가입에 휴대폰 인증 단계를 추가한다` | 표에 없는 타입을 사용했고, "-한다"로 끝남 | `feature: 회원 가입에 휴대폰 인증 단계를 추가` |
| `fix: 품절 상품 구매 버튼 숨김 처리함` | 조사를 생략했고, 의미가 없는 "처리함"을 덧붙임 | `fix: 품절된 상품의 구매 버튼을 숨김` |
| `feature: 주문 목록 페이지 크기 상한 맞추기` | 조사를 생략했고, "-기"로 끝나고, 상한이 얼마인지 알 수 없음 | `feature: 주문 목록의 페이지 크기를 최대 100건으로 제한` |
| `fix: 결제 리뷰 지적 반영 (중복 결제 차단, 재시도 간격 분리, 웹훅 검증 보강)` | 괄호 안에 항목을 나열했고, 변경 세 가지를 커밋 하나에 포함함 | `fix: 동일한 주문의 중복 결제를 차단` (나머지 변경은 각각 별도의 커밋으로 작성) |
| `fix: 쿠폰 발급 로직 개선 — 정책을 서비스로 · 일시 실패 503` | 엠대시와 가운뎃점을 사용했고, "개선"만으로는 무엇이 변경되었는지 알 수 없음 | `fix: 쿠폰 발급이 일시적으로 실패하면 503 을 반환` |

## 4. 커밋 본문

제목만으로 변경한 이유를 알 수 없을 때 본문을 작성합니다. 본문은 제목과 다르게 완성된 문장으로 작성하고, 문체는 해라체("-했다")를 사용합니다.

```
fix: 예외 로그의 경로에 포함된 URL 쿼리 값을 마스킹

스테이징 환경에서 쿼리에 식별용 값을 넣어 요청해 보니 예외 필터가 기록하는
path 에 그 값이 그대로 남아 있었다. 예외 필터도 접근 로그와 같은
함수(redactQuery)로 쿼리 값을 마스킹하도록 수정했다.
```

- 첫 문단에는 변경한 이유를 작성하고, 다음 문단에는 무엇을 어떻게 변경했는지를 작성합니다.
- 한 줄이 72자 안팎을 넘지 않도록 줄을 바꿉니다.
- 관련 이슈는 마지막 줄에 `Refs: #12` 또는 `Closes: #12` 형식으로 표시합니다.

## 5. PR 제목

PR 제목은 커밋 제목과 같은 규칙으로 작성합니다. 스쿼시 머지를 하면 PR 제목이 그대로 커밋 제목으로 사용되기 때문입니다. PR 에 커밋이 여러 개 포함되어 있다면 그 커밋들을 합친 결과 하나를 제목으로 작성합니다.

## 6. PR 본문

PR 본문은 **합니다체** 로 작성합니다. 커밋은 개발자가 변경 기록으로 읽는 글이고 PR 은 리뷰어와 배포 담당자에게 설명하는 글이므로 문체를 구분합니다. 해요체("추가했어요")는 사용하지 않습니다.

### 절 구성과 순서

절 이름과 순서는 아래와 같이 고정합니다. 절 이름은 그 절에 포함된 내용을 가리키는 명사로 작성하고, 읽는 사람에게 질문하는 형태("왜", "무엇이 바뀌나")로 작성하지 않습니다. 아래에 없는 이름(요약, 왜, 무엇을, 변경 내용, 검증, 확인, 테스트 계획, 배포 주의)은 사용하지 않습니다.

```markdown
## 작업 배경

<이 변경이 필요해진 상황과 이유. 2~4문장.>

## 변경 사항

- **<변경된 동작 한 가지>**: <어떻게 변경되는지 한두 문장>
- ...

## 배포 참고 사항

- <마이그레이션, 환경 변수, 배포 순서, 기존 데이터에 발생하는 변화>

## 확인 사항

- [x] <직접 실행해서 통과한 항목>
- [ ] <확인하지 못한 항목과 그 이유, 또는 배포한 뒤에 확인할 항목>
```

- **작업 배경**: 반드시 작성합니다. 이 변경이 필요해진 상황(누가 어떤 문제를 겪었는지, 무엇을 측정했는지)을 작성합니다. 변경한 내용은 다음 절에 작성하므로 여기에는 작성하지 않습니다. 관련 이슈나 이전 PR 은 이 절에서 링크합니다.
- **변경 사항**: 반드시 작성합니다. 이 PR 을 머지하면 동작이 어떻게 달라지는지를 작성하고, 변경한 파일을 나열하는 것으로 대신하지 않습니다. 항목마다 변경된 동작을 굵은 글씨로 먼저 작성하고 콜론 뒤에 설명을 작성합니다. 동작과 관련이 적은 변경은 마지막에 "그 밖에" 항목으로 모아서 작성합니다.
- **배포 참고 사항**: 마이그레이션, 환경 변수, 배포 순서, 기존 데이터의 변화가 있을 때에만 작성합니다. 해당하는 내용이 없으면 "없음"이라고 작성하지 않고 절 전체를 생략합니다.
- **확인 사항**: 반드시 작성합니다. 직접 실행한 명령과 그 결과(테스트 개수 포함)만 `[x]` 로 표시합니다. 확인하지 못한 항목은 생략하지 않고 `[ ]` 로 표시한 뒤 확인하지 못한 이유를 함께 작성합니다.
- 변경 규모가 작더라도 같은 절 구성을 사용하고, 각 절을 한 줄로 작성할 수 있습니다.

저장소에 PR 템플릿을 추가한다면 위 절 구성을 그대로 `.github/pull_request_template.md` 에 넣고, 절마다 작성 방법을 HTML 주석으로 안내합니다.

### 사용하지 않는 것

- 에이전트 세션 링크와 "Generated with" 같은 서명
- 이모지
- 아래 "사용하지 않는 기호" 절에 있는 기호
- "이 PR 은 ~을 합니다"처럼 정보가 없는 도입 문장
- 근거가 없는 평가("크게 개선했습니다", "안정성을 높였습니다"). 측정한 값이나 확인한 사실을 작성합니다
- 리뷰 지적 번호(D4, P2)만 표시한 항목. 무엇이 변경되었는지를 문장으로 작성합니다

### 사용하지 않는 기호

아래 기호는 단어 사이의 관계(그리고, 또는, 그래서, ~에서 ~로)를 문장으로 표현하지 않고 함축합니다. 읽는 사람이 그 관계를 추측해야 하므로 커밋 제목과 커밋 본문, PR 제목과 PR 본문에 사용하지 않습니다. 코드 블록, 인용한 원문, 파일 이름처럼 원문 그대로 표기해야 하는 부분에는 사용할 수 있습니다.

| 기호 | 이름 | 대신 사용하는 표현 |
|------|------|--------------------|
| `·` | 가운뎃점 | "와/과", "그리고", "또는", 쉼표 |
| `—` | 엠대시 | 콜론, "그래서", "즉", 또는 문장을 둘로 나누기 |
| `–` | 엔대시 | 범위에는 "~" 또는 "부터 ~까지", 그 밖에는 엠대시와 같은 표현 |
| `→` | 화살표 | "~에서 ~로", "~하면", "그다음에" |

| 나쁜 예 | 좋은 예 |
|---------|---------|
| `주문서·영수증 화면 추가` | `주문서 화면과 영수증 화면을 추가` |
| `CI 제한 시간 20분 → 35분` | `CI 제한 시간을 20분에서 35분으로 늘림` |
| `결제 실패 — 재시도 버튼 추가` | `결제에 실패하면 재시도 버튼을 표시` |
| `typecheck · lint · format:check 통과` | `typecheck, lint, format:check 통과` |

## 7. 좋은 PR 본문의 예

```markdown
## 작업 배경

#29 를 머지한 뒤 실제 서버(임시 PostgreSQL 에 마이그레이션과 시드 데이터를 적용한 환경)에
화면을 연동해서 시나리오 14개를 직접 실행했습니다. 금액 계산과 권한 검사는 모두
정상이었지만 다음 단계의 화면으로 이동할 방법이 없는 화면이 두 곳 있어서 수정합니다.

## 변경 사항

- **배송지가 없어서 결제할 수 없는 주문에서 배송지 입력 화면으로 바로 이동할 수 있습니다**:
  텍스트로만 표시하던 안내를 경고 영역과 "배송지 입력하기" 버튼으로 변경했습니다. 버튼을
  누르면 해당 주문의 배송지 입력 시트가 열린 상태로 이동합니다.
- **영수증을 발행한 주문은 취소 버튼을 비활성화합니다**: 기존에는 취소 사유를 모두 입력하고
  버튼을 누른 뒤에야 서버가 요청을 거절했다는 사실을 토스트 메시지로 확인할 수 있었습니다.
- 그 밖에: CI 제한 시간을 20분에서 35분으로 늘렸습니다. E2E 테스트가 333개로 늘어나면서
  #29 의 CI 실행이 제한 시간을 초과해 320번째 테스트에서 중단되었기 때문입니다.

## 확인 사항

- [x] 실제 서버에서 시나리오 14개 통과
- [x] `pnpm typecheck`, `lint`, `format:check` 통과, vitest 1,643개 통과
- [ ] 실제 PG 결제: 로컬 환경에서는 테스트 결제만 확인했습니다
```

## 8. 올리기 전에 점검할 항목

- [ ] 타입이 저장소의 commitlint 에서 허용되고 타입 표의 의미와 일치하는가
- [ ] 제목이 명사형(추가, 숨김, ~하게 함)으로 끝나고, 조사를 생략하지 않았고, 괄호 안에 항목을 나열하지 않았는가
- [ ] PR 본문이 합니다체이고 절 이름과 순서가 기준과 일치하는가
- [ ] "변경 사항"에 변경한 파일이 아니라 달라지는 동작을 작성했는가
- [ ] 확인하지 못한 항목을 `[ ]` 로 표시하고 이유를 작성했는가
- [ ] 세션 링크, 이모지, 가운뎃점(·), 엠대시(—), 엔대시(–), 화살표(→)가 없는가
- [ ] "어휘" 절의 표에 있는 표현이나 그와 비슷한 비유적 표현이 없는가
- [ ] 2번 절의 순서대로 natural-korean 스킬을 불러와서 모든 문장을 검사했는가
